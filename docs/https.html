部署 / HTTPS

HTTPS 与反向代理

墨忆的代码行为真的依赖请求头。这一页把每个头怎么影响逻辑讲清楚，然后给两份可直接抄的反代配置。

X-Forwarded-Proto 与 Cookie Secure

代码里的判定

lib/console.js:146-151 的 sessionCookie() 函数：

const proto = String((req && req.headers && req.headers['x-forwarded-proto']) || '')
  .split(',')[0].trim();
const secure = proto === 'https' ? '; Secure' : '';

它取 X-Forwarded-Proto 头的第一个逗号段，trim 后严格等于 'https' 才加 Secure 标志。为什么取第一段：这个头可能被多级代理追加成 https, http（客户端到第一跳是 HTTPS、第一跳到第二跳是 HTTP），取第一段拿到的是客户端实际用的协议。

后果

如果反代不传这个头，或者传了但值不对（比如 http），服务端发出的 Set-Cookie 就不带 Secure。这意味着：

  • 浏览器会通过 HTTP 明文链路发送会话 Cookie。
  • 同一网络里的任何人都能嗅探到 moyi_session 的值，直接拿来调 /api/console/* 接口。
  • 即使你的反代强制 HTTPS，只要没传 X-Forwarded-Proto: https，Cookie 依然没 Secure——浏览器不知道后面那层是加密的。

怎么自查

打开浏览器 DevTools → Application → Cookies，看 moyi_session 那一行的 Secure 列。如果是空的，说明服务端没加。或者 Network 面板里找登录响应，看 Set-Cookie 头里有没有 ; Secure。

修复方法

在反代配置里加 proxy_set_header X-Forwarded-Proto $scheme;（Nginx）或确认 Caddy 自动透传（Caddy 默认会加）。不要写死 https——如果反代自身监听 HTTP（比如内网），写死会让所有 Cookie 都带 Secure，而浏览器在 HTTP 页面上会拒绝发送 Secure Cookie，结果是谁都登不进去。

X-Forwarded-For 与限速 key

代码里的判定

lib/audit.js:125-131 的 clientKey() 函数：

const xff = req.headers['x-forwarded-for'];
const ip = (typeof xff === 'string' ? xff.split(',')[0].trim() : '')
  || (req.socket && req.socket.remoteAddress) || 'unknown';
return crypto.createHash('sha256').update(String(ip)).digest('hex').slice(0, 16);

限速 key 的来源：优先 X-Forwarded-For 的第一跳 IP，退回 req.socket.remoteAddress，再退回字符串 'unknown'。sha256 后取前 16 位十六进制作为匿名化标识。

代理不传 XFF 时所有用户共享一个限速桶

如果反代不透传 X-Forwarded-For，所有请求到达墨忆时 req.socket.remoteAddress 都是反代的内网地址（比如 172.17.0.1）。所有用户的限速 key 都一样——一个人触发注册限速，其他人也注册不了；一个人试错口令 10 次，所有管理员都被锁 15 分钟。

反过来，如果反代正确传 XFF，每个客户端的限速桶是独立的。

MOYI_ALLOWED_ORIGINS 与 CSRF

代码里的判定

lib/moyi.js:575-585 的 allowedOrigin() 函数：

const list = (process.env.MOYI_ALLOWED_ORIGINS || '').split(',').map(s => s.trim()).filter(Boolean);
const origin = req.headers.origin;
if (!origin) return null;
if (list.includes('*')) return '*';
const allow = new Set(list);
allow.add('http://localhost:3906');
allow.add('http://127.0.0.1:3906');
return allow.has(origin) ? origin : null;

默认行为：没有请求带 Origin 头时不返回 CORS 头（return null）。带了的，只有 MOYI_ALLOWED_ORIGINS 白名单里的、以及两个 localhost 地址被放行。其余一律不返回 Access-Control-Allow-Origin，浏览器会拦。

设成 * 的 CSRF 后果

如果 MOYI_ALLOWED_ORIGINS=*，任何网页都能以当前浏览器的身份调墨忆 API。墨忆有两道 CSRF 防护：Cookie SameSite=Strict 和写操作另需 X-Moyi-Console: 1 头。前者在同站跳转时仍然会带 Cookie（Strict 不防同源攻击），后者跨站 fetch 发不出自定义头——但 SameSite=Strict 在用户从同站的恶意页面点链接时不起作用。CORS * 把最后一道门拆了。

生产环境应该显式列出前端域名，比如 MOYI_ALLOWED_ORIGINS=https://moyi.example.com。

Nginx 配置

server {
    listen 80;
    server_name moyi.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    server_name moyi.example.com;

    ssl_certificate     /etc/lets/live/moyi.example.com/fullchain.pem;
    ssl_certificate_key /etc/lets/live/moyi.example.com/privkey.pem;

    # HSTS：一年，含子域，允许预加载
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains; preload" always;

    # 只转发墨忆端口，绝不转发 PostgREST
    location / {
        proxy_pass http://127.0.0.1:3906;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Connection        "";
        proxy_read_timeout 60s;
    }
}

要点：

  • HTTP 80 端口 301 跳到 HTTPS。
  • X-Forwarded-Proto $scheme——$scheme 是当前监听的协议，443 段里就是 https。
  • X-Forwarded-For $proxy_add_x_forwarded_for——追加客户端真实 IP。
  • 绝不转发 PostgREST 的 3001 端口。自托管栈的 PostgREST 只绑 127.0.0.1，如果你在这里加一个 location /pg/ 转发到 3001，等于把全库（含管理员口令哈希）公开到互联网。

Caddy 配置

moyi.example.com {
    reverse_proxy localhost:3906 {
        header_up X-Forwarded-For {remote_host}
        header_up X-Forwarded-Proto {scheme}
    }
}

Caddy 自动申请和续签 Let's Encrypt 证书、自动强制 HTTPS、自动加 HSTS。它默认会透传 X-Forwarded-For 和 X-Forwarded-Proto，上面显式写一遍是为了确保不被上游覆盖。

同样不要给 PostgREST 加 reverse_proxy 段。

反向代理与 read_only 容器

compose 里墨忆容器设了 read_only: true，根文件系统只读。这不影响反向代理——反代连的是容器的 3906 TCP 端口，与文件系统无关。

相关的环境变量：

MOYI_HOST

绑定地址，默认 0.0.0.0。容器内一般不用改。

MOYI_PORT

容器内监听端口，默认 3906。Dockerfile 里 EXPOSE 3906，改了这里要同步改 compose 的端口映射。

MOYI_HOST_PORT

宿主机映射端口，默认 3906。反代 proxy_pass 指向这个端口。

三者关系：MOYI_HOST:MOYI_PORT 是容器内监听地址，MOYI_HOST_PORT 是宿主机端口，反代连宿主机端口。
