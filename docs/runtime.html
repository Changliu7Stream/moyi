环境与部署 / Runtime Detection

环境自动识别

「我这个部署到底被墨忆认成了哪种环境？」——这一页回答的就是这个问题。墨忆的环境识别分布在六个层面：启动时算基址、启动自检、库侧状态、请求级头信息、检索后端、以及缺表时的降级梯度。每一层的判据、默认值、判错后的症状都列在下面。搞清这六层，绝大多数「起不来 / 打不通 / 静默失效」都能自己定位。

层面识别什么依据判错的典型症状
① 启动时存储后端与路径前缀MOYI_DB_URL 主机名 + MOYI_DB_BACKEND全站 404 / 全站 500
② 启动自检关键凭据是否齐、能否当掌柜变量是否非空（不校验格式）横幅有 ⚠，或横幅干净却处处 500
③ 运行期·库侧表在不在、装过没有HTTP 404 / 唯一冲突 409 / settings 缺表引导页该出没出、该封不封
④ 运行期·请求侧这个请求走没走 HTTPS、来自哪个 IPX-Forwarded-Proto / X-Forwarded-ForCookie 丢 Secure、限速串成一桶

① 存储后端与路径前缀怎么推断

墨忆只依赖 PostgREST 协议，所以它不需要知道「数据库是什么」，只需要算出一个能用的 REST 基址。基址 = URL 去掉尾斜杠 + 推断出的前缀。前缀的推断是一条有先后顺序的四分支判断：

function inferPrefix(url):
  1. MOYI_DB_PREFIX 已设置（哪怕设成空串）        → 直接用它，不再推断
  2. URL 的 pathname 已以 /rest/v1 结尾           → 返回 ''（避免拼成 /rest/v1/rest/v1）
  3. MOYI_DB_BACKEND == 'supabase'                → 返回 '/rest/v1'
  4. URL 主机名匹配 /\.supabase\.(co|in)$/i        → '/rest/v1'，否则 → ''

三条要点值得单独强调：

  • 第 1 步判的是「有没有设置」，不是「值真不真」。用 !== undefined 判断，所以 MOYI_DB_PREFIX=（显式空）会关闭推断并把前缀定为空。想强制无前缀就写空串，想让它自己推断就别设这个变量——这两种写法行为不同，很容易搞反。
  • 第 2 步是为了容错。有人把 SUPABASE_URL 填成项目根，有人习惯连 /rest/v1 一起填。这一条让两种写法都能工作。
  • 第 4 步只认 .co 和 .in。自建域名前置的 Supabase（CDN/自定义域）不会被认出来，此时要么设 MOYI_DB_BACKEND=supabase，要么直接写全 MOYI_DB_PREFIX=/rest/v1。
你填的 URL其它设置推断出的前缀最终打到的地址
https://abc.supabase.co—/rest/v1…supabase.co/rest/v1/memories
https://abc.supabase.co/rest/v1—''（命中第 2 步）…/rest/v1/memories（不重复）
http://127.0.0.1:3000—''http://127.0.0.1:3000/memories
https://pg.my-cdn.com（Supabase 套壳）BACKEND=supabase/rest/v1…/rest/v1/memories
https://api.example.com/db（反代加了前缀）DB_PREFIX=/db/db（强制）…/db/memories
127.0.0.1:3000（漏了 scheme）—''fetch 报非法 URL → 500

② 启动自检：它查什么、不查什么

服务启动时打印横幅。自检逻辑很浅——只判断关键变量是否非空，绝不校验格式，也绝不真的连一次库。这是有意的取舍：启动路径不该依赖网络可达性，否则凭据写错会导致容器反复重启而不是给出可读错误。

横幅输出触发条件该怎么办
⚠ 缺少环境变量: MOYI_DB_URLMOYI_DB_URL 与 SUPABASE_URL 都为空（提示哪个名字，取决于它认自己是哪种后端）补第 1 组变量
⚠ 缺少环境变量: MOYI_DB_TOKEN三个 token 名（MOYI_DB_TOKEN/SUPABASE_KEY/SUPABASE_ANON_KEY）全为空补 token；自托管填任意非空串也行
ⓘ 未设置 MOYI_CODE，任何人都无法注册为 master（安全默认）MOYI_CODE 与 MASTER_CODE 都没设这不是错误。只有需要 master 管理能力时才设
存储: Supabase（托管） / 存储: PostgREST（自托管/兼容协议）它自我认定的后端类型若与你预期不符，回去看①

「横幅干净」不等于「配置对」

自检不校验 URL 格式、不测连通性、不验 token 有效性。所以漏写 http://、主机名打错、token 填了已轮换的旧值——横幅全绿，服务正常监听，直到第一个真打库的请求才回 500。判断配置是否真的通了，用自查命令里的 curl /api/console/status 看 db_ready，那才是实测结果。

③ 库侧状态：/api/console/status 的每个字段

引导安装页就是靠这个公开、免认证的接口决定自己该不该出现。判定完全在服务端，前端藏不掉也绕不过。注意别和 /api/status 混——后者是 Agent 面的，要带 X-Moyi-Key。

字段类型怎么算出来的含义
needs_setupbool!表缺失 && !settings缺失 && !有管理员 && !已落锁是否该展示引导页。四个条件全满足才为真
has_adminsboolSELECT id FROM admins LIMIT 1 有行库里是否已有管理员
db_readybool!表缺失 && !settings缺失迁移 SQL 跑过了吗
setup_lockedboolsettings.setup_locked 为真 || has_admins安装入口是否已永久封存。注意它带 || has_admins：有管理员就视为已锁，即使锁行丢了也拦得住重装
instance_namestringsettings，缺省 墨忆实例显示名，最长 40 字符（超出截断）
open_registerboolsettings.open_register === '1'公开注册是否开着
global_memoryboolsettings.global_memory === '1'跨 Agent 只读可见是否开启
authenticatedbool会话 Cookie 是否有效当前浏览器是否已登录
role / usernamestring｜null取自会话对应的管理员行未登录时为 null

真值表：为什么 needs_setup 要四个条件

关键在于「表还没建」和「装好了」这两件事不能混淆。若只看 has_admins，用户在没跑迁移 SQL 时会看到一个能提交、但必然失败的引导页，提交后得到一堆莫名其妙的错误。

settings 表admins 表有管理员已落锁db_readyneeds_setup这是什么处境
缺缺否否falsefalse没跑迁移 SQL。安装页不该出现
缺在是否falsefalsesettings 表被删了；管理台降级但 Agent 功能照常
在在否否truetrue干净的新实例，等人来装
在在是是truefalse正常已安装（绝大多数情况）
在在是否truefalse锁行被误删，但仍有管理员 → setup_locked 靠 || has_admins 兜住
在在否是truefalse⚠ 锁了但一个管理员都没有（管理员被删光、锁行还在）→ 安装口封死，只能手工恢复

最后那一行是真实的运维风险

setup_locked=1 存在、但 admins 表被清空时，needs_setup 仍是 false：引导页不会重新出现，你也无法自助建管理员。恢复只能手工做（见口令恢复：先插一行 role='super' 的管理员再登录）。反过来说，删掉 setup_locked 这一行就重新打开了安装入口——任何能写库的人都能给自己造一个超管，所以这条要当作高危操作对待。

并发安装怎么抢：唯一冲突当 CAS

两个人同时打开引导页都点了安装，不能变出两个「首个超管」。落锁靠的是往 settings 插一行 setup_locked，而该表以 key 为主键：

1先探一次读 settings，表缺失→409 提示先跑 SQL；已落锁→409 提示装过了
→
2建管理员username 唯一约束同样会 409
→
3插锁行POST settings；主键冲突回 409 即「有人比我先」
→
4失败方回滚删掉自己刚建的管理员，回 409「刚刚已被安装」

第 3、4 步是关键：绝不留下「建了管理员但没落锁」的中间态。另外安装者勾的选项（实例名、是否开放注册）用 upsert 写而非裸 POST——迁移 SQL 已经预插了 instance_name/open_register 两行，裸 POST 会撞 409 且因为 return=minimal 无人检查状态码，症状是装完发现勾掉的选项静默丢失。

④ 请求级环境：两个 Forwarded 头

墨忆自己不听 443，HTTPS 总是由反向代理终结。所以「这个请求是不是加密来的」「客户端真实 IP 是谁」只能从代理传进来的头里读。

X-Forwarded-Proto → 会话 Cookie 的 Secure

const proto = String(req.headers['x-forwarded-proto'] || '').split(',')[0].trim();
const secure = proto === 'https' ? '; Secure' : '';
// moyi_session=<token>; Path=/; HttpOnly; SameSite=Strict; Max-Age=…[; Secure]

代理链可能把多级 hop 拼成 x-forwarded-proto: https, http，所以取第一段（最外层、用户实际看到的协议）。

代理不传这个头 → Cookie 永远不带 Secure

后果是明文链路上会话 token 可被嗅探重放。自查：登录后看响应头 Set-Cookie 末尾有没有 ; Secure。没有就说明代理没正确传 X-Forwarded-Proto，或你本来就在用 http 访问。配置见HTTPS 与反向代理。

反过来，客户端伪造 X-Forwarded-Proto: https 并不会造成安全漏洞——最坏是他自己拿到一个 http 下发不出去的 Cookie。

X-Forwarded-For → 限速的 key 来源

const xff = req.headers['x-forwarded-for'];
const ip = (typeof xff === 'string' ? xff.split(',')[0].trim() : '')
        || (req.socket && req.socket.remoteAddress) || 'unknown';
return sha256(ip).slice(0, 16);   // 不落明文 IP

限速按这个哈希值分桶：注册限速、Agent 认证失败、管理台口令失败各用独立前缀（reg:h:、reg:d:、auth:、adminauth:），互不顶掉配额。

代理不传 XFF 时，所有用户共享同一个限速桶

没有 X-Forwarded-For 就退回 socket.remoteAddress——而在反向代理后面，这个地址永远是代理自己。于是「每小时 10 次注册」变成「全体用户加起来每小时 10 次」：第 11 个人什么也没干就拿 429。多用户部署务必让代理传真实客户端 IP（Nginx proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;）。

另一面也要清楚：XFF 由客户端可控时，攻击者每次换个假 IP 就能绕开限速。所以这层只是提高成本的软防线，真正的暴破拦截应放在代理层或防火墙。

⑤ 检索后端的自动识别与降级

墨忆能在两种检索实现间切换，并在响应里如实标注用的哪条路，不让你猜：

search_backend含义条件
pgvectorDB 端近邻召回（走 match_memories() + HNSW）MOYI_DB_SEARCH=1 且 RPC 调用成功
scan服务层暴力扫描（拉 ≤MOYI_SCAN_LIMIT 条在内存算）默认；或下推被关；或 RPC 不可用而自动回退

熔断是进程级且不复位

RPC 第一次返回 404/400 就把 rpcUnavailable 置真，之后本进程不再尝试下推（免得每条查询都去撞一次 404）。所以：补建了 match_memories 函数后，必须重启墨忆进程，光改 MOYI_DB_SEARCH=1 不够——旧进程还记着「RPC 不可用」。

⑥ 表缺失时的降级梯度

PostgREST 对未知关系回 404 + code 42P01。墨忆把这种「表不存在」和「查询结果为空」严格区分开，并逐层降级，而不是笼统报错：

缺失的表识别到的状态行为
settingssettingsMissing=true用默认设置继续跑；管理台与全局记忆不可用；stderr 只警告一次；db_ready:false、needs_setup:false；Agent 侧功能不受影响
adminstableMissing（本请求内判定）登录/安装回 409 并明确提示「跑 sql/00-schema.sql，Supabase 再补 sql/vector-search.sql」，而不是报一个看不懂的错
两者都缺—db_ready:false；安装请求直接 409 并说明缺 settings，且不会留下半成品管理员
match_memories 函数进程级熔断检索永久回退 scan（直到重启），响应里 search_backend 仍是诚实的 scan

设计取向是：宁可少给一个功能，也不要给一个看起来能用、提交后必然失败的界面。缺表是可修的部署问题，不该伪装成运行时错误。

「我这是哪种环境」决策树

1URL 主机名里有 supabase.co/.in？有 → 云路线，前缀自动加 /rest/v1，跑 sql/00-schema.sql + sql/vector-search.sql
→
2没有 supabase 域名，那 PostgREST 是自己的吗？是 → 自托管全栈，跑 sql/00-schema.sql + docker/init/10-roles.sql
→

一个原则

任何时候怀疑环境判断有问题，先看 /api/console/status 的输出。它把墨忆眼里的那个世界讲清楚了：库通不通、装没装过、有没有登录、三个开关各是什么状态。这比读日志或猜配置快得多。
