文档站上线 GitHub Pages

这一页讲的是文档站自身的部署，不是墨忆服务的部署（那在四条部署路径）。它要解决的问题只有一个：怎么让 docs/ 里的 16 个 HTML 变成一个可以被别人访问的网站，以及为什么会踩坑。

这套文档的部署前提

零构建、零依赖、零配置。没有 package.json、没有打包步骤、没有 CI。仓库里的 docs/ 就是产物本身，GitHub Pages 直接把它当静态文件发。所以「部署失败」的原因几乎只可能是配置选错，而不是构建出错。

开启：Settings → Pages，三步

1仓库 Settings → Pages侧栏 Code, planning and automation 分组下的 Pages。需要 admin 或 maintainer 权限
→
2Source 选 Deploy from a branch另一个选项 GitHub Actions 是给需要构建流程的站点用的；本站不需要
→
3Branch: main ／ Folder: /docsSave。约 10 秒到 1 分钟后顶部出现站点地址

站点地址是 https://<owner>.github.io/moyi/（项目站固定落在 /<repo>/ 下）。注意路径里没有 /docs——发布源选 /docs 的意思是「以那个目录作为站点根」，不是「挂在 /docs 下」。所以文档首页是 …/moyi/，…/moyi/docs/ 反而是 404。

Folder 为什么必须选 /docs，不能选 /（root）

选根目录等于把整个代码仓库发布成公开网站

发布源选 / 时，Pages 会读仓库根目录的全部内容。server.js、sql/、test/ 这些当然无所谓，但一旦哪天有人往仓库里提交了不该公开的东西，它就会跟着发出去。而且 GitHub 官方文档明确警告：Pages 站点在公网上始终可访问，即使仓库是私有仓库（私有仓库需要付费套餐才能开 Pages，但站点本身不是私有的）。所以发布源要收窄到 /docs。

另一点：Folder 下拉里只有 /（root） 和 /docs 两个选项——Pages 不接受任意子目录作为发布源。这就是文档站必须放在 docs/ 而不是 site/ 或 website/ 的原因，没有商量余地。

.nojekyll 为什么必须存在

从分支发布时，Pages 默认按 Jekyll 处理（除非 build_type 指定为不需要构建）。本站是纯手写 HTML，Jekyll 在这里只有破坏性、没有好处：

不写 .nojekyll 会怎样机制
下划线开头的文件被静默丢掉Jekyll 约定 _* 与 .* 是源文件／元文件，不进输出。本文档曾有个 docs/_inventory.md 草稿，正好落在这条规则里
含 {{ 或 {% 的正文可能整页构建失败Markdown/HTML 会过 Liquid 模板解析器，未闭合的花括号是解析错误。文档里写代码片段时很容易碰上
目录里缺 index.html 时行为不可预期Jekyll 会尝试生成站点地图与 permalink，而不是原样直出

放一个空文件 docs/.nojekyll 即可，GitHub 见到它就跳过 Jekyll，直接按静态文件发。它已经在仓库里。

.nojekyll 必须被 git 跟踪

它是隐藏文件，.gitignore 里如果有 .* 之类的规则会把它排除掉——那样本地有、仓库没有，Pages 依旧走 Jekyll。提交后到仓库页面确认 docs/.nojekyll 真的在。本站 .gitignore 没有这类规则，但你自己改过就得复核。

全部链接必须是相对路径

这是本站最容易埋雷的一条。项目站挂在 /<repo>/ 子路径下，而本地预览挂在根（python -m http.server 起在 docs/ 时，页面在 http://127.0.0.1:8000/env.html）。绝对路径 /env.html 在本地能用，上线就 404——它会指向 https://<owner>.github.io/env.html，那是你的用户站（如果有），不是项目站。

<!-- ✗ 本地正常，Pages 上 404 -->
<link rel="stylesheet" href="/assets/docs.css">
<a href="/env.html">环境变量</a>

<!-- ✓ 两种落点都对 -->
<link rel="stylesheet" href="assets/docs.css">
<a href="env.html">环境变量</a>

本站的写法：每个页面顶部声明 <div class="d-wrap"><main>，侧栏、顶栏、搜索、上下页全部由 assets/docs.js 在运行时注入，链接清单集中在文件开头一个 NAV 数组里。这样「相对路径」这件事只需要在一处保证，不会 16 个页面各抄一遍、改一处漏十五处。

新增一页要改哪里

  1. 建 docs/新页面.html，照现有页面写骨架（<!DOCTYPE html>、lang="zh-CN"、data-ver="v3.3"、viewport-fit=cover、assets/docs.css、底部 assets/docs.js）。
  2. 在 docs/assets/docs.js 的 NAV 里加一行 { href: '新页面.html', text: '…' }。
  3. 正文里给 <h2> 手动写 id（写 id 的会保留，不写的由 JS 按中文标题生成 slug）。

只改这两处，导航、搜索索引、上下页链接、页脚自动跟上。不要在任何页面里手写侧栏 HTML。

不开网页，用 API 一次性开启

适合脚本化，或者你想连着推送一起做。需要 repo 权限的凭据（classic PAT 勾 repo；fine-grained PAT 需要 Pages: Read and write 加 Administration: Read and write 两个权限）。

# 1) 创建 Pages 站点，发布源 main + /docs
curl -L -X POST \
  -H "Accept: application/vnd.github+json" \
  -H "Authorization: Bearer $GH_TOKEN" \
  -H "X-GitHub-Api-Version: 2022-11-28" \
  https://api.github.com/repos/Changliu7Stream/moyi/pages \
  -d '{"source":{"branch":"main","path":"/docs"},"build_type":"legacy"}'

# 2) 查状态：html_url 就是站点地址，status 变 built 即上线
curl -L -H "Accept: application/vnd.github+json" \
  -H "Authorization: Bearer $GH_TOKEN" \
  https://api.github.com/repos/Changliu7Stream/moyi/pages

# 3) 已经建好但源选错了，改源（PUT 时 path 是必填）
curl -L -X PUT \
  -H "Accept: application/vnd.github+json" \
  -H "Authorization: Bearer $GH_TOKEN" \
  https://api.github.com/repos/Changliu7Stream/moyi/pages \
  -d '{"source":{"branch":"main","path":"/docs"},"https_enforced":true}'
响应码含义怎么办
201已创建正常，去查状态
409站点已存在改用 PUT，别重复 POST
422校验失败九成是 path 写成了 docs（要写 /docs），或分支不存在
403权限不够token 缺 Administration 写权限，或缺仓库 admin 身份

token 不要写进仓库、命令行历史或 compose 文件

用环境变量传（$GH_TOKEN），用完在 GitHub 上撤销。这条和项目本身的原则一致：能写库的凭据绝不落到会被同步、会被打印的地方——和数据库配置为什么只能待在环境变量里是同一个理由。

改完文档没生效？手动催一次构建

# 相当于「不提交新 commit 也重新构建一次」
curl -L -X POST -H "Accept: application/vnd.github+json" \
  -H "Authorization: Bearer $GH_TOKEN" \
  https://api.github.com/repos/Changliu7Stream/moyi/pages/builds

# 看最近一次构建结果，error.message 会写失败原因
curl -L -H "Accept: application/vnd.github+json" \
  https://api.github.com/repos/Changliu7Stream/moyi/pages/builds/latest

构建请求限「每仓库同时一个、每人同时一个」，连着点会排队甚至被拒；先查 builds/latest 再决定要不要催。

上线后自查清单

检查怎么看不通过说明
首页能开访问 https://<owner>.github.io/moyi/404 → 发布源没配对，或仓库里没有 docs/index.html
样式生效看页面是不是水墨风；DevTools 里 assets/docs.css 状态 200404 → 有人写了绝对路径，或 assets/ 没提交
侧栏出现左侧有分组目录、顶部有搜索框没有 → docs.js 未加载（检查脚本标签或仓库里是否缺文件）
跨页链接点几个页面间链接404 → 路径写成了 /x.html；见相对路径
站内搜索搜「X-Forwarded-Proto」应有命中提示「索引不可用」→ 只会在 file:// 下出现，http 访问不该有
HTTPS 强制用 http:// 访问应跳 https没跳 → PUT 时补 "https_enforced":true

排查顺序

Pages 的问题几乎全在这四类里，按顺序排：

现象最可能原因动作
整站 404，设置页显示「Your site is live at …」DNS/CDN 边缘还没同步，或首次构建仍在排队等 1 分钟；查 builds/latest 的 status
提示缺少 /docs 文件夹的构建错误docs/ 从发布分支上被删了或没提交git ls-files docs | head 确认文件在 main 上
部分页面 404、样式丢失绝对路径，或 assets/ 未跟踪按自查清单逐条走
内容显示成原始文本、下划线文件不见了Jekyll 仍在处理 → .nojekyll 没进仓库确认 docs/.nojekyll 已被 git 跟踪并推到 main
仓库是私有的，站点却公开可见Pages 站点本身不设访问控制这不是故障，是 Pages 的行为。文档站不含秘密，但别把含凭据的文件放进 docs/

本地先看一眼再推，成本几乎为零：

cd docs && python3 -m http.server 8099 --bind 127.0.0.1
# 浏览器打开 http://127.0.0.1:8099/

本站全部链接是相对路径，所以本地 http 下看到的效果与线上一致——唯一的差别是本地挂在根，绝对路径这种错误反而看不出来。这也是清单里要先查跨页链接的原因：真正的判据是「有没有人写了以 / 开头的 href」。

Pages 不负责什么

文档站是静态文件，跟墨忆服务没有部署关系

Pages 只发 docs/。它不会运行 Node、不会提供 /api/*、不会代理到数据库。管理台（/console）仍然只在墨忆服务自己的部署里（Docker / Vercel / 裸进程）。把文档站地址当成管理台地址去访问是打不开的。

两条实际影响：

  • 文档里的接口示例都用 http://localhost:3906 作占位，读者要自己换成部署后的地址。文档站不做「点一下就在真实实例上跑一次」的交互演示——那需要一个公开的墨忆实例，等于把演示库交给所有访客。
  • 站内搜索靠 docs.js 用 fetch 抓同目录各页正文现建索引，纯前端。页面总量在这个量级下没问题；将来涨到几十页再换成预生成的 index.json。

最短路径复述

① 确认 docs/.nojekyll 和 16 个 HTML 已提交并推送到 main（本地 commit 不会触发构建）；② Settings → Pages → Deploy from a branch → main + /docs → Save；③ 打开 https://<owner>.github.io/moyi/ 按自查清单过一遍。
