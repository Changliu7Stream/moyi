数据库结构

墨忆一共五张表：agents、memories、admins、admin_sessions、settings，外加两个 SQL 函数。本页以 sql/00-schema.sql 与 docker/init/10-roles.sql 为权威，逐列、逐索引讲清「为什么长这样」。

五张表

agents — 持有 API Key 的工具身份

列类型约束 / 默认为什么
iduuidPK, gen_random_uuid()Agent 是机器创建、机器引用，UUID 避免自增 ID 暴露数量与枚举风险
nametextNOT NULL显示用，允许重名——name 不参与认证
api_key_hashtextNOT NULL存 sha256 而非原文。用 text 而非 bytea 是因为 PostgREST 对 bytea 的 hex 编码处理不如 text 直观
roletextNOT NULL, 默认 'agent'取值 agent / master，由服务层控制，数据库无 CHECK 约束——master 的 key 允许多个共存，部分索引已承担唯一性语义
created_attimestamptzNOT NULL, now()审计排序用

memories — 记忆条目

列类型约束 / 默认为什么
idtextPK格式 mem_ + 16 位 hex。用 text 而非 uuid：ID 由服务层生成（非数据库），text 允许前缀标识类型，便于日志排查
agent_iduuidNOT NULL, FK → agents ON DELETE CASCADE归属。级联删除：删 Agent 时记忆一并清除，不留孤儿行
contenttextNOT NULL记忆正文，上限 20000 字符由服务层校验
summarytext可空自动截断的摘要，列表页展示用
importancetextNOT NULL, 默认 'medium', CHECK IN ('high','medium','low')决定衰减速度与同步策略。CHECK 约束在数据库层兜底，防止服务层 bug 写入非法值
tagstext[]NOT NULL, 默认 '{}'关键词标签数组，PostgreSQL 原生数组类型，支持 @> 包含查询
sourcetext可空来源标记（mcp / api / force 等），排查用
syncedbooleanNOT NULL, 默认 false是否已同步到外部存储。high 重要性默认 true
synced_attimestamptz可空最近一次同步时间
access_countintegerNOT NULL, 默认 0访问计数，衰减算法的输入之一
created_attimestamptzNOT NULL, now()创建时间
updated_attimestamptz可空最近更新。NULL 表示从未修改
embeddingvector(384)可空语义向量。384 维与 lib/embeddings.js 的 DIM 常量必须一致；旧行可能为 NULL（尚未回填）

admins — 管理控制台的人

列类型约束 / 默认为什么
iduuidPK, gen_random_uuid()与 agents 分开的主键空间
usernametextNOT NULL UNIQUE登录名，唯一
password_hashtextNOT NULLscrypt 自描述格式：scrypt$N$r$p$salt$hash。永不下发前端
roletextNOT NULL, 默认 'admin', CHECK IN ('super','admin')super 可管人，admin 只管自己的会话和口令
disabledbooleanNOT NULL, 默认 false停用开关。停用后 session_version 被推到极大值，旧会话立刻作废
session_versionbigintNOT NULL, 默认 0改口令或停用时 +1。会话行携带创建时的版本号，版本不符即失效——无需吊销列表即可「退出所有设备」
created_attimestamptzNOT NULL, now()审计用

admin_sessions — 管理台会话

列类型约束 / 默认为什么
iduuidPK会话行 ID，用于前端标注「本次会话」
admin_iduuidNOT NULL, FK → admins ON DELETE CASCADE归属管理员
token_hashtextNOT NULL UNIQUE存 token 的 sha256，不存原文。UNIQUE 约束同时充当查找索引
session_versionbigintNOT NULL, 默认 0创建时快照 admins.session_version。口令一改，旧行的版本号就对不上
expires_attimestamptzNOT NULL会话过期时间，由 MOYI_SESSION_DAYS 控制
created_attimestamptzNOT NULL, now()审计用

settings — 实例级配置

列类型约束 / 默认为什么
keytextPK一行一个键。键名白名单在服务层控制
valuetextNOT NULL统一存 text，布尔用 '0'/'1'——避免多列反复 ALTER
updated_attimestamptzNOT NULL, now()最后修改时间

初始种子行：instance_name='墨忆'、global_memory='0'、open_register='1'。

setup_locked 这一行同时充当「已安装」的 CAS 锁。引导页安装成功后写入该行，后续安装请求因唯一约束 409 被拒。删掉这一行等于重新打开安装入口——任何人访问引导页都能再建一个超管。

为什么 memory 的 id 是 text 而 agent 的 id 是 uuid

Agent 是数据库自己生成的（gen_random_uuid()），用 uuid 天然合适。记忆条目是服务层生成的（mem_ + hex），用 text 能保留前缀标识，便于在日志和 URL 里一眼区分 ID 类型。两个主键空间互不干扰。

SQL 函数

match_memories — 向量近邻检索

match_memories(
  query_embedding vector(384),
  match_agent_id  uuid,
  match_count     int DEFAULT 20,
  min_similarity  float DEFAULT 0.10
) RETURNS TABLE (
  id, agent_id, content, summary, importance, tags, source,
  synced, access_count, created_at, updated_at, similarity
)
-- SECURITY INVOKER, SET search_path = public, pg_temp

match_agent_id 传 NULL = 不限定 agent（全局记忆模式）。similarity 由 1 - cosine_distance 算出，值域 (0, 1]。函数本身不做权限校验，归属过滤由调用方（墨忆服务层）负责。

increment_access — 访问计数原子自增

increment_access(p_id text) RETURNS void
-- SECURITY INVOKER, SET search_path = public, pg_temp

消除服务层「读-改-写」的并发窗口。优先走 RPC，函数不存在时退回读-改-写。

自托管 vs Supabase：权限模型差异

自托管栈下 PostgREST 绝不能暴露公网

docker/init/10-roles.sql 给 web_anon 授了全部五张表的 SELECT/INSERT/UPDATE/DELETE。不开 RLS 意味着：拿到 anon token 就能直接读 admins.password_hash——那是人挑的口令的 scrypt 哈希，可离线爆破。这不是理论风险，是架构决定的。

维度自托管（00-schema + 10-roles）Supabase（vector-search）
RLS关。信任边界在墨忆服务层开。五张表全部 ENABLE
web_anon 权限五张表全量 CRUD + 两个函数 EXECUTE无任何权限（无 policy = 默认拒绝）
service_role不存在这个角色显式 policy 全量放行
admins 暴露风险PostgREST 暴露 = 口令哈希库公开RLS 默认拒绝，anon 读不到
admin_sessions_token_idx有（冗余，见上）无
memories_synced_idx有无

自托管栈的真实 GRANT 语句（docker/init/10-roles.sql）：

GRANT USAGE ON SCHEMA public TO web_anon, authenticated;
GRANT SELECT, INSERT, UPDATE, DELETE ON public.agents  TO web_anon, authenticated;
GRANT SELECT, INSERT, UPDATE, DELETE ON public.memories TO web_anon, authenticated;
GRANT SELECT, INSERT, UPDATE, DELETE ON public.settings TO web_anon, authenticated;
GRANT SELECT, INSERT, UPDATE, DELETE ON public.admins TO web_anon, authenticated;
GRANT SELECT, INSERT, UPDATE, DELETE ON public.admin_sessions TO web_anon, authenticated;
GRANT EXECUTE ON FUNCTION public.increment_access(text) TO web_anon, authenticated;
GRANT EXECUTE ON FUNCTION public.match_memories(vector(384), uuid, int, float) TO web_anon, authenticated;

Supabase 路线的对应策略（sql/vector-search.sql，须先跑过 sql/00-schema.sql 建表）：五张表全部 ENABLE ROW LEVEL SECURITY，每张表只建一条 FOR ALL TO service_role USING (true) 的策略，不建任何面向 anon / authenticated 的 policy——默认拒绝。

为什么墨忆只依赖 PostgREST 协议

墨忆不认识「数据库」，只认识「PostgREST 协议的 HTTP 接口」。所有存储操作都是 fetch(REST + path, opts)——自托管的 PostgREST 和 Supabase 托管的 PostgREST 可以互换，代码一行不改。差异只在 URL 形态和路径前缀（Supabase 挂 /rest/v1，原生 PostgREST 挂根路径）。

两套 SQL 不能混着跑

早期版本把整个 ./sql 目录挂进 docker-entrypoint-initdb.d，结果 vector-search.sql 也被执行了——那份给两张表开 RLS 且默认拒绝 anon，于是自托管栈表现为「所有记忆凭空消失」（每条读都是 0 行，且不报错）。现在 docker-compose 只精确挂载 00-schema.sql + 10-roles.sql。

迁移与升级

  • 所有语句使用 IF NOT EXISTS / OR REPLACE，可重复执行。
  • 从旧版升级：00-schema.sql 幂等，重跑一遍补建缺表；自托管再跑 10-roles.sql（授权），Supabase 再跑 vector-search.sql（RLS + RPC）。全新库两种后端都必须先跑 00-schema.sql。
  • embedding 列是后加的（ALTER TABLE ... ADD COLUMN IF NOT EXISTS），旧库升级不会丢数据，但需要回填向量（POST /admin/backfill-embeddings）。
  • setup_locked 行删了会重开安装入口——正常情况下不需要碰它。
