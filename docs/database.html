数据库与环境支持

「我用 MySQL 行不行」「能不能不装 PostgREST」「Cloudflare 支持吗」——这三类问题都在这一页收口。分两半：上半讲数据库，下半讲运行时环境支持矩阵。表结构和 SQL 细节见 数据库结构，各平台部署步骤见 部署路径。

一、为什么锁定 PostgreSQL + pgvector

墨忆的核心能力是语义检索：把文本编码成 384 维向量，再按余弦相似度召回。存这种向量并做近邻检索，最省事的方案是让数据库本身长一个向量类型——pgvector 就是 Postgres 的官方扩展。建表脚本 sql/00-schema.sql 里写死了三样东西：

CREATE EXTENSION IF NOT EXISTS vector;      -- 依赖 pgvector 扩展
embedding  vector(384)                       -- 记忆表的向量列，固定 384 维
USING hnsw (embedding vector_cosine_ops)    -- HNSW 索引，加速近邻检索

这意味着存储后端只有 PostgreSQL + pgvector 一种。MySQL、SQLite、MongoDB、Cloudflare D1 都不支持这个向量类型和 HNSW 索引，接不上。MOYI_EMBED_DIM 默认 384，但可改：它必须与数据库 memories.embedding 列的 vector(<dim>) 取同一个值（两处分别改，见 改向量维度）。接 BGE 这类语义更强的 provider 时，模型输出维度往往是 768/1024，改维度正是接入的关键一步。

二、墨忆连的不是数据库，是 PostgREST

理解这一点，很多困惑会自动消失：墨忆代码里没有任何 Postgres 驱动，它只用 fetch 打一个符合 PostgREST 协议的 HTTP 接口。PostgREST 是一个把 Postgres 表直接暴露成 REST 端点的组件。所以：

  • 你不必「给墨忆装 Postgres」，你要装的是PostgREST（或一个用它包装过的服务）。
  • Supabase 底层就是 Postgres + PostgREST，所以墨忆能直连 Supabase——它俩说的是同一套协议。
  • 只要某个服务对外提供 PostgREST 风格的接口（同一套 select= / or= 查询语法、同一个 Prefer 头、RPC 走 POST /rpc/xxx），墨忆就能连，与它背后是不是原生 Postgres 无关。这也是「自托管 PostgREST」和「Supabase 托管」可以互换、代码一行不改的原因。

哪些是墨忆真正会打到的接口

核心只用到几张表的增删改查，加上两个数据库端函数（RPC）：match_memories（近邻检索）和 increment_access（访问计数）。RPC 缺失时墨忆会自动退回服务层扫描检索，并在响应的 search_backend 字段里如实标成 scan——不会因为你的库没建全就直接 500。细节见 数据库结构。

三、两份 SQL：建表 + 安全层

初始化一个库要按顺序跑两份 SQL，职责不同、顺序不能反：

文件建什么幂等？
sql/00-schema.sql七张表（agents / memories / admins / admin_sessions / oauth_tokens / oauth_codes / settings）+ 装 vector 扩展 + HNSW 索引 + match_memories / increment_access 两个 RPC。其中 oauth_* 两张仅开启 MCP 浏览器授权 时才会被读写是
sql/vector-search.sql给七张表 开 RLS、只放行 service_role；并以 IF NOT EXISTS 兜底重建三张控制台表和两张 oauth 表、重建两个 RPC（为「表已存在」的旧库升级准备）是

只跑 vector-search.sql 会留下半套库

它是给「表已存在的旧版」做升级用的，不建 agents/memories。全新库单跑它，SQL 编辑器逐句执行，会给你建好三张管理台表、却对缺失的表报错——得到一个「看着装好了、其实检索和计数全废」的库，比干净失败更难查。务必先 00-schema.sql 再 vector-search.sql。

自托管路线还多一步：跑 docker/init/10-roles.sql 建 web_anon 角色并收紧 GRANT。自托管刻意不跑 vector-search.sql（不开 RLS），原因见下一节。

四、两种权限模型：Supabase 开 RLS，自托管不开

墨忆的「Agent 之间互相看不到对方记忆」这件事，在服务层（readFilter）已经做了。数据库层的 RLS 是额外兜底，两家需求相反：

路线RLS为什么
Supabase开anon key 会随前端分发，任何拿到它的人都能直连 PostgREST。不开 RLS，anon key 等于全库读写、绕过一切隔离。所以 vector-search.sql 开 RLS 且默认全拒，只放行 service_role。
自托管 PostgREST不开PostgREST 只绑 127.0.0.1、公网不可达，隔离在服务层做就够。关键：若误在自托管库开了 RLS 却没有面向 web_anon 的策略，每条读都会返回 0 行且不报错——表现成「所有记忆凭空消失」。

两套 SQL 的 RLS 策略相反，不能混用。Docker 自托管栈因此只精确挂载 00-schema.sql 和 10-roles.sql 两个文件，绝不把 sql/ 整个目录挂进 initdb（那会把 Supabase 专用的 vector-search.sql 也执行了）。细节见 部署 · 自托管。

五、运行时环境支持矩阵

「环境」有两层含义，别混：一层是数据从哪来（上面几节），另一层是墨忆进程跑在哪（下表）。第二层决定限速、审计这些「依赖进程内存」的能力还能不能用。颜色：绿＝功能完整，黄＝能用但有退化／有前提，红＝跑不了。

运行环境支持度限速 / 审计入口
Docker（cloud / local）完整有效（单长驻进程）quickstart A/B
裸 Node（服务器）完整有效（单长驻进程）quickstart C
Vercel Serverless可用·有退化每实例独立，多实例可绕过；审计实例回收即失部署 · Vercel
Cloudflare Workers / Pages Functions可用·仅付费版同无状态退化，且冷隔离更频繁部署 · Cloudflare
GitHub Pages不支持跑服务—纯静态托管，仅用于这份文档站，见 Pages 部署

Cloudflare 为什么是「仅付费版」

墨忆的口令哈希用 scrypt（N=16384），实测单次约几十毫秒 CPU。Cloudflare Workers 免费版每次调用 CPU 上限仅 10ms，登录/注册会被 Error 1102 掐断；付费版默认 30s 才够。代码路径已实现并本地测试，部署步骤见 部署 · Cloudflare。

六、改向量维度（接入 BGE 等 provider）

默认 384 维适合内置本地向量与 bge-small。要接语义更强的模型（bge-base=768、bge-large/bge-m3=1024、OpenAI=1536），维度必须三处对齐：

  1. 服务端：MOYI_EMBED_DIM 设成模型输出维度；MOYI_EMBED_URL/MOYI_EMBED_KEY/MOYI_EMBED_MODEL 填 provider 信息。多数 BGE 部署不接受请求里的 dimensions 参数，保持 MOYI_EMBED_SEND_DIM 为空即可。
  2. 数据库列：把 sql/00-schema.sql 或 sql/vector-search.sql 顶部「维度常量」v_dim 改成同一个值，重建 embedding 列。
  3. 回填：旧向量与新维度不在同一空间，用新维度重建列后，跑 POST /api/admin/backfill-embeddings（master，带 {"overwrite": true}）全量重刷。

RPC match_memories 的入参已改为无维度 vector，改维度时不需要重建函数——只要列维度对得上即可。

改维度是破坏性操作

重建 embedding 列会清空已有向量，务必先完成第 1 步的服务端配置、再重建列、最后回填，顺序不能反。维度对不上时，写入会被拒并静默降级本地哈希向量，看似成功实则语义失效。

七、明确不支持什么

  • 非 Postgres 系数据库：MySQL / SQL Server / MongoDB / SQLite / Cloudflare D1——没有 pgvector，接不上。
  • 纯静态托管跑服务：GitHub Pages、Cloudflare Pages 的静态部分、Netlify 静态——它们不跑 Node，只能托管文档/前端，跑不了墨忆 API。
  • 管理台里改数据库地址：刻意不做。连接信息只走环境变量，否则一次 XSS 就能把实例记忆流到攻击者的库（见管理台）。
