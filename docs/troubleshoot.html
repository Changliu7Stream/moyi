运维 / Troubleshoot

故障排查

按「症状 → 为什么 → 怎么办」组织。每条都有代码或文档依据，不是猜测。

启动横幅出现「⚠ 缺少环境变量」/「ⓘ 未设置 MOYI_CODE」

⚠ 缺少环境变量：server.js 启动自检发现 MOYI_DB_URL（或 SUPABASE_URL）和 MOYI_DB_TOKEN（或 SUPABASE_KEY）至少一组没填。后果是所有 API 调用返回 500，因为服务层拿不到后端地址或凭据。解决：检查 .env.local（裸 Node）或 data/moyi-env/moyi.env（Docker）里这几项是否拼写正确、文件是否被正确加载。

ⓘ 未设置 MOYI_CODE：这不是错误，是信息提示。不设 MOYI_CODE 意味着任何人都无法通过注册接口成为 master（安全默认）。如果你需要 master 角色，设一个长随机串；如果只用管理台发号，不设也行。

所有 API 都返回 500

三个可能原因，按概率排序：

  1. 环境变量没填——启动横幅会明确说缺哪项。解决后重启。
  2. 数据库连不上——MOYI_DB_URL 拼错、Supabase 项目暂停、自托管栈里 PostgREST 容器没起来。用 curl $MOYI_DB_URL/ 直接测一下后端是否可达。
  3. 迁移 SQL 没跑——表不存在时 PostgREST 返回 404，服务层把它当故障处理。去跑对应的 SQL（两条路都要 sql/00-schema.sql 建表；Supabase 再补 sql/vector-search.sql，自托管再补 docker/init/10-roles.sql）。

/status 里 db_ready:false、needs_setup:false 但库里确实没管理员

db_ready 为 false 意味着 admins 表或 settings 表至少有一个不存在（PostgREST 返回 404）。needs_setup 为 false 是因为代码里显式判断了 !tableMissing && !settingsMissing——表缺失时不算「待安装」，否则用户会在没跑迁移 SQL 的情况下看到一个能提交、但必然失败的引导页。

解决：跑迁移 SQL。Supabase 在 SQL Editor 里依次执行 sql/00-schema.sql 与 sql/vector-search.sql（只跑后者会留下半套库，见 部署详解）；自托管 psql -d moyi -f sql/00-schema.sql && psql -d moyi -f docker/init/10-roles.sql。

引导安装页返回 409「本实例已完成安装」

两种情况：

  1. 确实已经安装过了——admins 表里有行，或 settings 表里有 setup_locked 行。这是正常行为，用管理员账号登录即可。
  2. 你想重置安装——删 Cookie 没用，因为判定在服务端。删 settings 表里的 setup_locked 行可以重开安装入口，但这等于重新打开安装页，任何人都能立一个新管理员（见 SECURITY-MIGRATION.md）。正确的重置方式是：如果忘了口令，走下面的手工恢复流程，而不是删锁。

删 setup_locked 的风险

这一行是引导安装的写锁。删掉它 = 重开安装入口。在公网可达的实例上，这意味着任何人在你删锁到重新安装之间的窗口里，都能建一个自己的超管账号。除非你明确知道自己在做什么，否则不要删。

忘记管理员口令

没有远程重置接口，也不该有。恢复办法是直接改库：

# 1. 用新口令生成哈希（参数须与库里格式一致）
node -e "const c=require('./lib/console.js');c.hashPassword('新口令').then(console.log)"
# 输出形如 scrypt$16384$8$1$<salt_b64>$<hash_b64>

# 2. 更新数据库
UPDATE public.admins
   SET password_hash = '<上一步输出>',
       session_version = <当前值 + 1>,
       disabled = false
 WHERE username = '你的管理员名';

推高 session_version 是为了顺手作废该账号遗留的全部会话——sessionAlive() 比对版本号，不一致即失效。如果不 +1，旧设备上的浏览器还保持着登录态。

如果整个实例连一个可用超管都不剩（误删或停用），先手工插一行 role='super' 的管理员再登录。

注册返回 429 / 管理台登录返回 429

这是两套独立的计数器：

计数器键前缀默认限额环境变量
注册（每小时）reg:h:10 次/来源/小时MOYI_REGISTER_PER_HOUR
注册（每天）reg:d:30 次/来源/天MOYI_REGISTER_PER_DAY
Agent 认证失败auth:30 次/来源/15 分钟MOYI_AUTH_FAIL_PER_15MIN
管理台口令失败adminauth:10 次/来源/15 分钟MOYI_ADMIN_FAIL_PER_15MIN

「来源」由 X-Forwarded-For 第一跳或 socket.remoteAddress 的 sha256 前 16 位决定。反代不传 XFF 时所有用户共享一个桶（见 HTTPS 与反向代理）。

批量注册场景不要撞注册限速，改用 master 签发：POST /api/agents（带 master 的 X-Moyi-Key），不走注册限速。

检索结果里 search_backend 是 scan 而不是 pgvector

三个条件必须同时满足才会走 pgvector：

  1. MOYI_DB_SEARCH=1——默认是 0，必须显式开启。
  2. match_memories RPC 必须存在——迁移 SQL 跑过才会建。
  3. RPC 没被熔断——rpcUnavailable 是进程级变量，一旦 RPC 返回 404 或 400 就置位，后续请求不再尝试，直接回退 scan。重启进程才能重置。

自查：curl /api/memories/search 的响应里看 search_backend 字段。如果是 scan，先确认环境变量，再确认 RPC 存在（curl $MOYI_DB_URL/rpc/match_memories 应该返回 401 而不是 404），然后重启墨忆进程清掉熔断标记。

记忆没有向量 / needs_embedding 不为 0

历史记忆在接入 embedding provider 之前存的，embedding 列为 null。回填接口：POST /api/admin/backfill-embeddings（master 权限）。响应里 remaining 为 0 即回填完成。

换 provider 必须全量回填：不同模型的向量不在同一空间。旧模型生成的向量与新模型生成的向量混在一起，余弦相似度没有意义，语义排序会失效。回填时加 {"overwrite": true} 覆盖已有向量。

覆盖率查询：GET /api/embeddings/status，看 vectorized / missing / total。

管理台能打开但保存设置没反应

三个可能原因：

  1. 缺少 X-Moyi-Console: 1 头——所有管理台写操作都要求这个头（防 CSRF）。如果你用 curl 或自定义客户端调 PATCH /api/console/settings，必须带这个头，否则返回 403。
  2. 不是超管——PATCH /api/console/settings 要求 role='super'。普通管理员只能 GET 读设置，写操作返回 403。
  3. 多实例延迟——设置缓存在进程内存里，TTL 由 MOYI_SETTINGS_TTL_MS 控制（默认 5000ms）。Vercel 等多实例部署下，写入后其他实例最多 5 秒后才看到新值。同进程内的写入会立即失效缓存。

端口被占、EADDRINUSE

启动时报 Error: listen EADDRINUSE :::3906，说明 3906 端口已被占用。先查谁在听：

ss -tlnp | grep 3906
# 或
lsof -i :3906

常见原因：上一个墨忆进程没退干净、Docker 容器映射了同端口、其他服务占了 3906。杀掉占用进程，或用 MOYI_PORT=3907 换端口。

Docker 容器收不到停止信号

docker stop 超时 10 秒后 SIGKILL 强杀，说明容器没在 10 秒内优雅退出。原因通常是 entrypoint 脚本没用 exec 替换进程——如果入口脚本 fork 出 node 子进程，SIGTERM 发给脚本（PID 1），脚本不转发给子进程，node 收不到信号。

墨忆的 docker-entrypoint.sh 最后一行是 exec node server.js，用 exec 替换了 shell 进程，让 node 成为 PID 1，直接收 SIGTERM。如果你改过 entrypoint 或用了自定义启动脚本，确保最后一行是 exec 开头。

自托管栈「每条读都 0 行且不报错」

这是 部署详解 里那个坑的实际表现。原因：自托管栈的 PostgREST 以 web_anon 身份运行，而 sql/vector-search.sql（Supabase 专用）开了 RLS 且不建面向 anon 的策略。一旦这个 SQL 被错误执行，web_anon 的每条读都被 RLS 拒绝，返回空数组——服务层把空数组当成「没有记忆」，不报错。

解决：

  1. 确认你跑的是 sql/00-schema.sql + docker/init/10-roles.sql，不是 sql/vector-search.sql。
  2. 如果已经跑错了，关 RLS：ALTER TABLE public.memories DISABLE ROW LEVEL SECURITY;（五张表都要关），或者删库重建（docker compose down -v 删数据卷，重新 up）。

自查命令

以下命令可直接复制，把 <host> 换成你的域名或 localhost:3906。

# 1. 服务是否活着
curl -s http://<host>/api/console/status | python3 -m json.tool

# 2. 带 Key 验证身份
curl -s http://<host>/api/whoami \
  -H "X-Moyi-Key: moyi_xxxxxxxxxxxxxxxx" | python3 -m json.tool

# 3. 看监听端口
ss -tlnp | grep 3906

# 4. 看容器日志
docker compose logs --tail=50 moyi-local
# 或
docker logs --tail=50 <容器名或ID>

# 5. 直接测 PostgREST 是否可达（自托管栈）
curl -s http://127.0.0.1:3001/ | head -c 200

# 6. 看向量覆盖率
curl -s http://<host>/api/embeddings/status \
  -H "X-Moyi-Key: moyi_xxxxxxxxxxxxxxxx" | python3 -m json.tool
