接口清单

墨忆对外暴露两组接口，认证面完全分开、互不通用。Agent 面走 X-Moyi-Key，控制台面走会话 Cookie。管理员 Cookie 打 Agent 接口回 401，Agent Key 打控制台接口也回 401——这不是 bug，是刻意的隔离。

两套认证面

Agent 面控制台面
路径前缀/api/*（除 /api/console/*）/api/console/*
凭据X-Moyi-Key: moyi_xxx 或 Authorization: Bearer moyi_xxx（开启浏览器授权后还可 Bearer moat_xxx，见浏览器授权一节）用户名+口令 → 会话 Cookie（moyi_session）
密钥/口令存储API Key 的 sha256scrypt 哈希（自描述格式）
谁在用Agent 程序、MCP 客户端人，在浏览器里
能读记忆正文？只能读自己那套（全局模式下可读他人）读不到任何记忆正文
跨面生效？不能。管理员 Cookie 打 /api/memories 回 401，Agent Key 打 /api/console/me 也回 401

为什么不让一套凭据通吃

如果把 Agent Key 和管理员 Cookie 塞进同一个前缀，迟早出现「拿 Agent key 命中管理端点」的越权。分开以后，认证方式由路径唯一决定，读代码的人不用往下翻三屏才知道某个端点靠什么鉴权。（lib/moyi.js:619-631）

Agent 接口（/api/*）

以下所有接口（除注册与验证外）均要求有效的 X-Moyi-Key。认证失败统一回 {error}，不带 key 与带错 key 都回 401，但只有带了 key 且错了才计入限速。

MCP over HTTP（/api/mcp）

Agent 面还有一条特殊路径 /api/mcp：它是 MCP 协议的 Streamable HTTP 端点，客户端把 JSON-RPC 请求体直接 POST 过来，服务端在完成 X-Moyi-Key / Bearer 认证之后才派发到工具执行。工具实现复用同面的 REST 端点（内部自调用 route），逻辑与 REST 一份，作用域与鉴权规则完全一致。

HTTP 形态暴露的工具与资源

工具规范名共 12 个：记忆侧 memory_save、memory_recall、memory_search、memory_forget、memory_graph_query、memory_stats、memory_health、memory_scope_list、memory_audit_log（master only）；技能侧 skill_propose、skill_list、skill_read。tools/list 只回规范名；tools/call 接受若干历史别名（remember / retrieve_memory / search_memory / forget / memory_graph 等），别名不重复列出。

initialize 现在声明 capabilities: { tools: {}, resources: {} }。resources/list 把已发布技能（外加调用者自己的草稿）暴露成 moyi-skill://<name> 资源，resources/read 按 uri 回 {contents:[{uri, mimeType:"text/markdown", text}]}，找不到回 -32002；缺 skills 表时 resources/list 降级为空清单而非报错。

浏览器授权端点（/api/oauth/* 与 /.well-known/*）

这一组是 MCP 浏览器授权（OAuth 2.1 精简子集：授权码 + PKCE）的认证面。它早于 Agent Key 闸门被派发——否则「拿 code 需要先有 key、拿 key 需要先有 code」的死结解不开。未配置 MOYI_OAUTH_CLIENT_ID 时 /api/oauth/* 全部回 501，等于整块功能关闭；两份发现文档仍可访问，但会指向一个不可用的授权端点。

拿到 access token 之后

访问令牌是 moat_ 前缀，用法与静态 Key 完全同路：Authorization: Bearer moat_… 打 /api/mcp 或任意 Agent 接口。权限模型没有新增任何东西——它背后就是一个普通 Agent 行，作用域、隔离、审计全部沿用。

控制台接口（/api/console/*）

控制台是另一套认证面：Agent 用 API Key，管理员用口令 + 会话 Cookie。所有写操作（POST/PATCH/DELETE）额外要求 X-Moyi-Console: 1 头，缺则回 403。

Set-Cookie 属性

登录、安装、改口令成功后，响应带 Set-Cookie。确切属性串（lib/console.js:146-151）：

moyi_session=<token>; Path=/; HttpOnly; SameSite=Lax; Max-Age=<seconds>[; Secure]
  • HttpOnly：JS 读不到，防 XSS 偷 token
  • SameSite=Lax：跨站 POST/表单不带 Cookie，防 CSRF 第一层；Lax 允许「跨站顶层 GET 导航」带 Cookie，这是 MCP 浏览器授权跳转能识别出已登录管理员的前提
  • Secure：仅当 X-Forwarded-Proto: https 时追加（lib/console.js:147-148），详见HTTPS 与反向代理
  • Max-Age：默认 MOYI_SESSION_DAYS（7 天），上限 30 天（lib/console.js:95-98）

错误响应形状

所有错误回统一的 {error, hint?} 结构：

{
  "error": "密钥无效",
  "hint": "..."      // 可选，给排查方向
}

429 限速额外带 retry_after_ms：

{
  "error": "密钥校验失败次数过多，请 15 分钟后再试",
  "retry_after_ms": 892341
}

403 vs 404 的不对称

全局记忆模式下，PATCH/DELETE 他人的记忆回 403（存在但你不能动）；严格模式下回 404（不存在）。

这个不对称是刻意的：严格模式下做一次「无归属探测」会把状态码变成跨 agent 的存在性探针——攻击者猜一个 id，403 表示存在、404 表示不存在，等于白嫖一次跨域查询。全局模式下调用方本来就看得见这条记忆（读放宽），所以回 403 更诚实。（lib/moyi.js:1498-1509）

curl 示例

注册 Agent

curl -X POST https://moyi.example.com/api/agents/register \
  -H 'Content-Type: application/json' \
  -d '{"name": "青霜掌柜"}'

响应 201，api_key 字段只这一次可见。

remember（去重一步完成）

curl -X POST https://moyi.example.com/api/memories/remember \
  -H 'X-Moyi-Key: moyi_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxx' \
  -H 'Content-Type: application/json' \
  -d '{"content": "我喜欢在雨天写代码", "source": "claude-desktop"}'

语义检索

curl -X POST https://moyi.example.com/api/memories/search \
  -H 'X-Moyi-Key: moyi_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxx' \
  -H 'Content-Type: application/json' \
  -d '{"query": "编程偏好", "limit": 10}'

控制台登录 + 带 Cookie 调用

# 登录，拿 Cookie
curl -X POST https://moyi.example.com/api/console/login \
  -H 'X-Moyi-Console: 1' \
  -H 'Content-Type: application/json' \
  -c cookies.txt \
  -d '{"username": "admin", "password": "your-password"}'

# 带 Cookie 调管理接口
curl https://moyi.example.com/api/console/me \
  -b cookies.txt

# 写操作另需 X-Moyi-Console 头
curl -X POST https://moyi.example.com/api/console/agents \
  -H 'X-Moyi-Console: 1' \
  -H 'Content-Type: application/json' \
  -b cookies.txt \
  -d '{"name": "新 Agent"}'
