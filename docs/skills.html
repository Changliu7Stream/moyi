技能层

技能是一份份 SKILL.md 风格的说明文档，所有 Agent 读同一份公共层，用现成的连接 Key 就能读。它和记忆是两层：技能是公共只读，记忆是私有可写。Agent 能往技能层提交的只有草稿，放行与否永远是人点的。

为什么要有这一层

MCP 让 Agent 能连上墨忆读写记忆，但「怎么用一个工具、遵守什么流程」这类共享知识没有地方沉淀。技能层就是给这类说明书准备的：部署者放一次，接上来的每个 Agent 都能读到，不用每台客户端各配一份。它对齐业界 SKILL.md 约定（YAML frontmatter 里 name + description），墨忆本身不生成技能正文、不做检索打分——它是一个带审核闸门的存储与读取层。

两层模型：公共只读 vs 私有可写

这是理解技能层的关键。技能与记忆物理上就是两张表，没有任何外键或查询交集：

记忆 memories技能 skills
归属每个 Agent 一份，agent_id 硬隔离全局共享，所有 Agent 读同一份
可写性Agent 自由写Agent 只能写自己的草稿，发布须人工
作用域函数受 全局记忆开关影响读范围不走那套作用域，开关碰不到技能
语义检索 / 衰减 / 去重都会处理都不参与，技能不是记忆

所以「每个 Agent 各自独立记忆、互不干扰」这件事在技能层不需要额外实现——技能根本不流进 memories，检索打分、衰减降级、语义去重、全局记忆开关全都碰不到它。

生命周期：published / draft / rejected

一条技能只有一个 status 字段，三态：

  • published：人（管理台）放的，或 Agent 提交后经人审核放行的。出现在所有 Agent 的列表里。
  • draft：Agent 自己生成的。只有提交者自己能读到，必须有人在管理台点「发布」才进入公共层。
  • rejected：人否决过的。保留正文供追溯，但不再出现在任何列表里。

这道闸门是本功能的安全边界

能往公共层写，等价于能对所有 Agent 下指令——这是提示注入的放大器。墨忆的处置是把写权限收到最小：status、origin、agent_id 三个字段永远由服务端赋值，Agent 提交时无论传什么都不认，一律落成 draft。别人未发布的草稿对你返回 404（不是 403），连「它存在」都不暴露，免得变成探针。

Agent 侧：三个工具 + 一组 resources

Agent 用现成的那把 Key 访问技能层，HTTP（/api/mcp）和 stdio 两种 MCP 形态都有。工具规范名共三个：

工具作用说明
skill_list列出可见技能返回全部 published + 调用者自己的 draft
skill_read读某一份的正文按 name 取，只能读到 published 或自己的草稿
skill_propose提交一份草稿正文必填；name/description 可从 frontmatter 推断，推不出则如实报错

除此之外，MCP 的 resources 原语也接上了：每份可见技能暴露成 moyi-skill://<name> 资源（uri + name + title + description + mimeType: text/markdown）。resources/list 回清单，resources/read 按 uri 回正文，找不到回错误码 -32002。没跑迁移（缺 skills 表）时，resources/list 降级为空清单而不是报错——让客户端在技能层尚未就位时也能正常连上。

对应 REST 端点（/api/skills）逐条清单见 接口清单页。

管理台：公共层的唯一写入口

发布、审核、从 URL 导入都只在管理台「技能」页发生，权限取「任一已登录管理员」（审核是运维动作，不是超管专属）。要点：

  • 从 URL 导入：粘贴一个 SKILL.md 的链接，服务端抓取、自动识别 name/description 并填入表单。「预览」只看前 600 字，不落库；确认无误再点「整份导入」，由服务端重新完整抓取，前端不会存截断的正文。
  • 人直建即发布：管理员手工填正文保存，直接进 published——因为写公共层的责任由这个人承担。
  • 审核草稿：Agent 提交的草稿在这里看，点「发布」进公共层，点「驳回」落 rejected。
  • 刷新：有 source_url 的技能可一键回源；服务端比对新旧 sha256，内容没变则不写库。

管理台侧端点（/api/console/skills/*）逐条清单见 接口清单页。

URL 抓取的 SSRF 控制

「从 URL 导入 / 刷新」要去抓一个远程地址，这是最容易招 SSRF 的地方。墨忆用的是域名白名单，而不是「解析出 IP 后校验 IP」：

为什么不用 IP 校验

要在零依赖前提下用 IP 校验真正防住 DNS rebinding，必须自己拿 net/tls 按已验证的 IP 建连、手搓整个 HTTP 客户端——那等于把漏洞面从「想不周」换成「写不对」，风险更高。白名单把可达主机收敛成一个封闭集合，SSRF 面因而不存在。

白名单细节（默认只放 GitHub 原始内容域，可用 MOYI_SKILL_URL_HOSTS 扩展，见环境变量页）：

  • 每一跳重定向都重新过白名单：302 跳内网是这类抓取最省事的绕法，逐跳校验才堵得住；最多跟 3 跳。
  • 只允许默认端口，非 80/443 直接拒。
  • 子域条目（如 example.com）放行 a.example.com 但要求 https；只有精确写出的主机名才允许明文 http——这是本地自托管 Gitea 与测试用的形态。
  • GitHub 的 blob 链接自动改写成 raw 域（否则抓到的是带高亮的网页）；tree（目录）链接明确拒绝，语义不清。
  • 正文上限 200KB，超限直接拒不做截断——截断后的 markdown 语义可能已经反了，比拒收更危险。

这一版刻意没做的

墨忆不替你生成技能正文（不引 LLM，保持零依赖），也不对技能做向量检索或相似度合并——它是存储与读取层，不是第二个记忆系统。技能之间不支持递归抓取整个仓库（只收单个 .md），也不支持动态注册式的任意源。这些都留给后续里程碑。
