使用 / Agents & Memory

Agent 隔离与全局记忆

一台墨忆可以同时服务很多个 Agent。默认它们彼此完全看不见——各自的 Key、各自的记忆、各自的统计。需要跨 Agent 共享时，在管理台打开「全局记忆」，但那个开关只放宽读，不放宽写。

默认：彻底隔离

这是墨忆的立命之本。每个 Agent 注册时拿到一把独立 Key，所有读写都以「这把 Key 属于谁」为边界：

操作作用域实现
列表 / 检索 / 按 id 读只有自己的查询强制带 agent_id=eq.<自己的 id>
写入 / 改写 / 删除 / 同步只有自己的同上；跨 agent 根本命中不了行
语义去重合并只在自己那套里找重复findSimilar 硬编码 agent_id=eq.<aid>（lib/moyi.js:302）
衰减体检与降级落库只有自己的用强制的 OWN_SCOPE 快照，不受全局开关影响
统计 /api/stats只有自己的同样带归属过滤

换个角度说：甲 Agent 的 Key 泄漏，泄漏面就是甲的那一套记忆，不会连累乙和丙。

给多个 Agent 各配一份 MCP

MCP 客户端连墨忆有两种传输形态，可以同时配、各用各的——协议并不限制只能接一种：

形态怎么连适合
stdio（本地）客户端在你机器上拉起 mcp-server.js 进程，进程再打本服务的 /api/*Claude Desktop 这类要落地进程、能配 command 的桌面客户端
HTTP（远程）客户端直接连部署地址的 /api/mcp，凭 Authorization: Bearer <key> 鉴权支持「远程 MCP / Streamable HTTP」的客户端，免装 Node、免跑本地进程

形态一：stdio（本地薄壳）

「独立」落在配置上就是：一个 Agent 一份 env，两份配置除了 MOYI_KEY 之外可以完全一样。管理台的 Agent 页在每次创建/重置 Key 后，会直接产出可粘贴的片段：

{
  "mcpServers": {
    "moyi": {
      "command": "node",
      "args": ["/absolute/path/to/moyi/mcp-server.js"],
      "env": {
        "MOYI_API": "http://localhost:3906",
        "MOYI_KEY": "moyi_<这个 Agent 专属的 key>"
      }
    }
  }
}

把这份片段分别贴进不同客户端，它们就各自连到同一个墨忆、但读写各自的记忆。mcp-server.js 是个无状态的 stdio 薄壳，多开几份互不打架。

形态二：HTTP（远程，免安装）

如果客户端支持远程 MCP，直接填一段 url + Bearer 头即可，不用在本机跑任何进程。管理台弹出的「MCP 配置」里也会一并给出这段：

{
  "mcpServers": {
    "moyi": {
      "url": "https://<你的部署域名>/api/mcp",
      "headers": { "Authorization": "Bearer moyi_<这个 Agent 专属的 key>" }
    }
  }
}

这条 /api/mcp 走的是 MCP 的 Streamable HTTP 传输：客户端把 JSON-RPC 请求（initialize / tools/list / tools/call 等）POST 过来，服务端复用与 REST 完全相同的鉴权和作用域逻辑后回 JSON。鉴权用的还是同一把 moyi_… Key，因此每把 Key 依旧只管自己那套记忆，隔离规则和 stdio 一模一样。

HTTP 形态暴露的工具名

/api/mcp 的 tools/list 返回规范工具名：memory_save、memory_recall、memory_search、memory_forget、memory_graph_query、memory_stats、memory_health、memory_scope_list、memory_audit_log。其中 memory_audit_log 仅超管 Key 可用。stdio 形态沿用其历史工具名（remember / search_memory 等），两者都映射到同一批 REST 接口。

别图省事共用一把 Key

两个 Agent 用同一把 Key，就等于它们共享同一套记忆——彼此的私人备忘互相可见、互相去重合并、互相影响衰减排序。要隔离就得一号一钥。真要共享，正确的做法是开全局记忆（下面），而不是合用凭据。这一条对 stdio 和 HTTP 两种形态都成立。

Key 泄露或想断开某个 Agent：管理台点「重置 Key」，旧 Key 立即失效；「删除」则连 Agent 记录和它的全部记忆一起级联删除（ON DELETE CASCADE），不可逆。

浏览器授权（OAuth 2.1，可选）

上面两种形态共用同一把 moyi_… Key，都要先手工复制粘贴。如果你的 MCP 客户端支持远程 HTTP + OAuth（按 MCP 规范走发现文档），可以省掉这一步：客户端自己拉起浏览器，你在已登录的管理台里点一下「同意」，它就拿走一把专属 token。这条路径要服务端先开启：MOYI_OAUTH_CLIENT_ID 设一个约定的 client_id（详见环境变量页），未设则整块功能关闭。

它解决的是「发钥匙」这一步，不是换一套权限模型

授权通过后，服务端为该客户端新建一个专属 Agent（名字形如 oauth:<client_id>），签发的 access token 通过 oauth_tokens 表映射到这个 Agent。之后它读写记忆的作用域、隔离规则，和你在管理台手动建一个 Agent 一模一样——没有多给任何权限。撤销也走同一条路：管理台删掉这个 Agent，它的 token 随之级联失效（鉴权结果有 5 秒进程内缓存，所以「失效」在全实例上的最大延迟是 5 秒，与实例设置缓存同一量级）。

三个协议端点，全部挂在 Agent 面的 /api/oauth/* 下、在普通 Key 闸门之前处理：

端点方法作用
/api/oauth/authorizeGET校验参数后返回同意页（未登录则给「先去管理台登录」页）
/api/oauth/approvePOST同意页表单提交：同意→建 Agent + 302 回跳带 code；拒绝→302 带 error=access_denied
/api/oauth/tokenPOST授权码 + PKCE verifier 换 access_token/refresh_token，或用 refresh 续期

另有两个 RFC 发现文档，供客户端自动找到上面的端点：

  • /.well-known/oauth-authorization-server —— 授权服务器元数据（各端点地址、只支持 code 流程与 S256）。
  • /.well-known/oauth-protected-resource —— 受保护资源元数据（指向 /api/mcp）。开了 OAuth 后，/api/mcp 的 401 响应会带 WWW-Authenticate: Bearer resource_metadata="…" 头，客户端据此发起授权。

这一版刻意没做的：动态注册与细粒度 scope

client_id 与 redirect_uri 白名单由服务端环境变量写死，不支持 RFC 7591 动态注册；token 是整实例一个 mcp scope，不分读写。授权同意人固定是「已登录的管理员」，因为墨忆没有 Agent 侧的浏览器登录。这几项都留给后续里程碑。

安全边界：PKCE 强制 S256，授权码一次性、60 秒过期；redirect_uri 必须精确命中白名单，拒绝带 #fragment 或 user@ 的地址（防开放重定向）；同意表单额外校验 Origin 等于本站。token 只存 sha256 哈希，明文只在签发瞬间出现一次。端点逐条清单见 接口清单页的浏览器授权一节。

全局记忆：只放宽「能读到谁」

管理台 → 设置 → 打开「全局记忆」。生效范围用一句话概括：

读扩到全库，写锁在自己

作用域的实现就一个函数：readFilter(aid, settings) —— 严格模式返回 agent_id=eq.<aid>，全局模式返回空串（不加过滤）。而所有写路径不使用这个函数，它们永远显式带 agent_id=eq.<aid>。

行为严格模式（默认）全局记忆开启后
列表 / 检索只有自己的看到所有人的，标注归属
按 id 读别人的404（与「不存在」不可区分）200，带 _read_only: true
改写别人的404403「只读：这条记忆属于其他 Agent」
删除别人的404403，且不执行删除
同步别人的404403
去重合并只在自己那套里找仍然只在自己那套里找
衰减 / 遗忘只扫自己的只扫自己的（用 OWN_SCOPE）
访问计数只有自己读到才涨别人读到不涨你的计数
图谱自己那套的共现图随读作用域放宽（会包含他人节点）

为什么写侧不一起放宽

不是因为偷懒。跨 Agent 的写会造成数据损坏，而不是带来便利：

  • 去重合并会污染归属。甲说「用户喜欢猫」、乙说「用户对猫过敏」，若允许跨 agent 合并，两条事实会被糅进同一条记录、写进其中一人的名下，两个 Agent 的上下文就此串味。
  • 衰减会互相牵制。让 A 的 /decay/apply 去降级 B 的记忆，等于 A 能改写 B 的记忆优先级——那是越权写，不是共享。
  • 访问计数决定衰减速度。若他人的读取也算进你的计数，一条被某个高频 Agent 反复扫到的记忆会「假装自己很有活力」，衰减模型就失真了。所以自增只在归属者自己读到时发生。

403 与 404 的不对称，是故意的

同一件「碰别人记忆」的事，两种模式给的状态码不同，这不是疏忽：

模式跨 agent 写理由
严格404隔离模式必须连「这条存在」都不透露。若回 403「存在但你不能改」，就成了存在性探针，可用状态码差异把别人的记忆 id 逐个枚举出来
全局403此模式下「别人的记忆存在」本来就是公开事实（列表里就能看到），所以可以给一个更诚实、更好排查的答复

关掉全局记忆后，之前那些 403 会退回 404——但数据一条都没少（测试专门回归了这点）。

怎么判断自己读到的是谁的

全局模式下，返回条目会带三个辅助字段：

{
  "id": "mem_a1",
  "content": "用户喜欢喝无糖乌龙茶",
  "scope": "global",        // 本次检索的作用域
  "_own": false,            // 是不是我自己的
  "_owner": "claude-desktop", // 归属者的名字（查不到时回落到 agent_id）
  "_read_only": true        // 别人的条目一律标只读
}

归属者名字来自 agents 表的 id → name 映射，带 60 秒进程内缓存，避免每次列表都多打一次库。

⚠️ 它是隐私边界，不是权限边界

开全局记忆前请先接受这一条

全局记忆让任何一个 Agent 都能读到全库记忆。这意味着：任何一把 Agent Key 泄露，泄露的就是全部人的记忆，而不只是那一个 Agent 的。原本「一号一钥、各管各的」提供的爆炸半径控制，在这一步被取消了。

它解决的只是「要不要让编程助手看见日程助手的记忆」这个隐私问题，不是「谁能改谁的数据」这个权限问题——后者由写侧锁定继续兜住。所以：

  • 只在同一个信任域里开（比如全是你自己的 Agent、共享同一份用户画像本来就合理）。
  • 不要为了「方便查看别人的记忆」而开着——那是 _owner 标注能解决的临时需求，长期开着就多一份泄漏面。
  • 开了之后，Key 的保管标准要按「全库钥匙」来衡量，而不是「单个 Agent 的钥匙」。
  • 关掉它只需在设置里关，不会改动任何数据，也不会清掉别人的访问计数。

配套开关：要不要开放公开注册

设置里另一个与 Agent 有关的开关。关掉之后：

请求结果
POST /api/agents/register（不带口令）403，注册闸门拦下
同上，带正确的 master_code201 放行——闸门不该把自己人也锁在门外
同上，带错误的 master_code403（与「闸门关着」同形，不给探测口令的反馈）
管理台创建 Agent不受此开关影响，照常

公网可达的实例建议关掉公开注册，改由管理台发号。无论开关状态如何，注册接口始终受 MOYI_REGISTER_PER_HOUR（默认 10/小时）限速——它是公开接口，只能限速不能真关。

怎么实测隔离是否生效

两个 Agent 各建一把 Key，然后：

# 甲记一条带明显指纹的记忆
curl -s -X POST $API/api/memories/remember \
  -H "X-Moyi-Key: $KEY_A" -H 'Content-Type: application/json' \
  -d '{"content":"甲的专属暗号：紫金山天文台观测编号 ZJ-7741","force":true}'

# 乙去搜 → 严格模式应当搜不到
curl -s -X POST $API/api/memories/search \
  -H "X-Moyi-Key: $KEY_B" -H 'Content-Type: application/json' \
  -d '{"query":"紫金山天文台观测编号 ZJ-7741"}'
# 期望：results 为空，且 scope 为 "own"

# 管理台打开全局记忆后，同样的请求 → 能搜到，且带 _own:false / _read_only:true / scope:"global"
# 再让乙试着改它 → 期望 403
curl -s -X PATCH $API/api/memories/mem_a1 \
  -H "X-Moyi-Key: $KEY_B" -H 'Content-Type: application/json' \
  -d '{"content":"被乙改掉了"}'

# 关键收尾：确认甲的内容原样未变（403 必须真的什么都没写）
curl -s $API/api/memories/mem_a1 -H "X-Moyi-Key: $KEY_A"

最后那一步别省

判断隔离是否有效，光看状态码不够——要回到归属者那边确认数据没被动过。集成测试里正是这么断言的（「越权写尝试后内容原样未变」）。
