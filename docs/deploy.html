部署 / Deploy

三条部署路径

墨忆只认识 PostgREST 协议，所以「数据库在哪」这件事可以换。三条路径的代码是同一份，差异全在 SQL 怎么跑、凭据从哪来、进程模型是长驻还是无状态。

连外部 Supabase

跑哪个 SQL：全新库要跑两份，顺序不能反

只跑 vector-search.sql 会留下半套数据库

全新项目里 agents / memories 两张表还不存在，而 sql/vector-search.sql 第一件事就是给它们开 RLS。空库单跑该文件的实测结果：所有触及这两张表的语句全部报 ERROR: relation "public.agents" does not exist（第 18、19、29、33、105、109、112、122、160 行），但 admins / admin_sessions / settings 三张表照建、RLS 照开——SQL 编辑器是逐句执行的，不会因为前面报错就停下。于是你得到一个看起来跑完了的库：控制台能用、能装能登录，而 embedding 列、HNSW 索引、match_memories 与 increment_access 两个 RPC 全都不存在，向量检索与访问计数静默降级或失效。这比干净地失败更难查。

该文件不建 agents / memories，这点它自己的头注释写得很明白——它是给表已存在的旧版墨忆做升级用的。

正确顺序，SQL Editor 里按次粘贴执行：

sql/00-schema.sql        -- 1. 建全部五张表 + pgvector 扩展 + HNSW 索引
sql/vector-search.sql    -- 2. 开 RLS、补控制台相关表、建两个 RPC

分工是这样：00-schema.sql 建 agents / memories / admins / admin_sessions / settings 五张表并装扩展；vector-search.sql 负责给五张表开 RLS、建 match_memories 与 increment_access 两个 RPC。后者对前者的产物只补不建，所以顺序反了会失败，跑对了则幂等——重复执行只出 NOTICE，不报错。老库升级（表已在）可以只跑第二份。

为什么这个 SQL 开 RLS

Supabase 项目天然是多租户的：anon key 会随前端代码分发，任何拿到它的人都能直连 PostgREST。如果不开 RLS，anon key 等于全库读写权限——墨忆的 agent 隔离会被完全绕过。sql/vector-search.sql 因此对所有表 ENABLE ROW LEVEL SECURITY，且不建任何面向 anon 的策略，默认全拒。只有 service_role key 通过显式 policy 被放行。

service_role key 绝不能进浏览器

这个 key 绕过 RLS 的一切检查。它只能出现在服务端环境变量里（SUPABASE_KEY 或 MOYI_DB_TOKEN），不能写进前端代码、不能写进 MCP 客户端配置、不能打进 Docker 镜像层。一旦泄露，立刻去 Supabase 后台 Settings → API → Rotate。

凭据怎么给墨忆

三个环境变量：

SUPABASE_URL 必填

别名 MOYI_DB_URL（优先）

项目地址，形如 https://xxxx.supabase.co。服务层据此自动补 /rest/v1 前缀。

SUPABASE_KEY 必填

别名 MOYI_DB_TOKEN（优先）/ SUPABASE_ANON_KEY

必须是 service_role key。anon key 会让每条读静默返回 0 行。

MOYI_CODE 建议

别名 MASTER_CODE

注册 master 的口令。不设则无人能成为 master（安全默认）。

Docker 路径下把这三项写进 data/moyi-env/moyi.env，docker compose --profile cloud up -d --build 即起。裸 Node 路径下写进 .env.local，node server.js 即起。

自托管全栈

compose 的两个 profile 为什么互斥

docker-compose.yml 定义了两个 profile：cloud 只起墨忆一个容器连外部 Supabase，local 起 Postgres + PostgREST + 墨忆三个容器。两个 profile 下的墨忆服务都要占宿主机的 3906 端口（MOYI_HOST_PORT 默认值），同时开会直接端口冲突——compose 会报错，这是有意的，响失败比静默二选一安全。

data/moyi-env/ 只读挂载的作用

compose 里 ./data/moyi-env:/data/moyi-env:ro 把凭据目录以只读方式挂进容器。入口脚本 docker-entrypoint.sh 遍历目录下所有 *.env 与 moyi.env，逐行解析后 export——不用 eval 不用 source，文件名和值里的 shell 元字符不会被执行。只读挂载保证容器内进程无法篡改凭据文件，这是容器化部署的安全底线。

容器本身也以非 root 用户 moyi 运行、根文件系统 read_only: true、no-new-privileges:true、只给 /tmp 开了 tmpfs。server.js 全程只 readFileSync 不写盘，所以锁根文件系统不会出问题。

为什么只精确挂载两个 SQL 文件

compose 里 postgres 容器的 volumes 长这样：

volumes:
  - pgdata:/var/lib/postgresql/data
  - ./sql/00-schema.sql:/docker-entrypoint-initdb.d/00-schema.sql:ro
  - ./docker/init/10-roles.sql:/docker-entrypoint-initdb.d/10-roles.sql:ro

注释里那个警告不是小题大做：docker-entrypoint-initdb.d 会执行目录下所有 .sql。如果你把 ./sql 整个目录挂进去，sql/vector-search.sql 也会被执行——而那个文件是 Supabase 专用的，它开 RLS 且默认拒绝 anon。自托管栈的 PostgREST 以 web_anon 身份运行，一旦 RLS 开启而没有面向 web_anon 的策略，每条读都返回 0 行，且不报错。表现是「所有记忆凭空消失」，而不是 401 或 500。

「每条读都 0 行且不报错」的坑

自托管栈刻意不开 RLS——隔离在服务层，PostgREST 只有一个 web_anon 角色，权限由 docker/init/10-roles.sql 的 GRANT 收紧。Supabase 栈刻意开 RLS——因为 anon key 会泄露，必须在数据库侧兜住。两套 SQL 的 RLS 策略相反，混用必出事。所以 compose 只精确挂载两个文件，不挂目录。

PostgREST 为什么只绑 127.0.0.1

docker-compose.yml 里 PostgREST 端口映射是 127.0.0.1:3001:3000。自托管栈不开 RLS，PostgREST 没有 agent 隔离概念——它落到公网等于全库公开，包括 admins.password_hash（scrypt 哈希，可离线暴破）。所以 PostgREST 只监听 loopback，由墨忆容器通过 Docker 内网 http://postgrest:3000 访问。要把管理面暴露到不可信网络，请在 admins / admin_sessions 上自己写 RLS 策略，或启用 PGRST_JWT_SECRET 并用 node scripts/gen-jwt.js 签发 JWT 作为 MOYI_DB_TOKEN。

Vercel Serverless

入口与路由

api/index.js 是 Vercel Function 入口，薄壳——require lib/moyi.js 的 route() 函数，把 Vercel 的 req/res 透传进去。vercel.json 两条 rewrite：

{ "source": "/api/(.*)", "destination": "/api/index" }
{ "source": "/console", "destination": "/console.html" }

所有 /api/* 请求都打到同一个 Function，route() 内部根据路径分发。/console 指向静态 HTML，管理台前端是纯 HTML/CSS/JS，不需要服务端渲染。

管理台为什么在无状态平台上仍可用

会话（admin_sessions 表）和设置（settings 表）都存在数据库里，不依赖进程状态。Vercel Function 冷启动时从数据库读会话哈希、比对版本号，与长驻进程走的是同一套逻辑。所以引导安装、登录、改设置、管 Agent 在 Vercel 上都能用。

限速与审计的退化

限速计数器（lib/audit.js 的 windows Map）和审计日志（同文件的 events 环形缓冲）都在进程内存里。Vercel 会起多个 Function 实例、随时回收，每个实例各自计数。后果：

  • MOYI_REGISTER_PER_HOUR（默认 10）和 MOYI_AUTH_FAIL_PER_15MIN（Agent 侧，默认 30）在单实例上有效，多实例下攻击者分散请求就能绕过。
  • MOYI_ADMIN_FAIL_PER_15MIN（管理台口令，默认 10）同理——无状态平台上的暴破拦截只是部分防线。
  • 审计日志在实例回收时丢失，不能作为合规留痕。

要可靠的限速，请放反向代理（见 HTTPS 与反向代理）或用 Docker 长驻进程那条路。

环境变量怎么配

Vercel 面板 → Settings → Environment Variables，配以下三项（Production + Preview 都勾上）：

MOYI_DB_URL 或 SUPABASE_URL 必填

Supabase 项目地址。Vercel 部署一般走 Supabase 路线。

MOYI_DB_TOKEN 或 SUPABASE_KEY 必填

service_role key。

MOYI_CODE 建议

master 注册口令。

可选：MOYI_EMBED_URL / MOYI_EMBED_KEY 接 embedding provider，MOYI_ALLOWED_ORIGINS 配 CORS 白名单。

选择建议

三条路线没有绝对的好坏，只有适不适合。几个典型场景：

  • 个人开发者，想快速跑起来试试：Supabase 路线。五分钟能注册项目、跑 SQL、起容器，不用管数据库备份和升级。限速在单实例下够用。
  • 小团队内部用，数据敏感：自托管路线。数据完全在自己手里，Postgres 可以做定期备份、审计日志可以接外部系统。运维成本高一些，但可控。
  • Demo 或低频个人用：Vercel 路线。零运维，自动 HTTPS，但限速和审计在多实例下基本失效。如果你的 Agent 一天只调几十次 API，问题不大。
  • 生产环境，多用户：自托管或 Supabase + 反向代理。Vercel 的限速退化在这种场景下是真实的安全风险——攻击者可以分散请求绕过每实例的计数。

一个常见的误区是「先用 Vercel 跑起来，以后迁移到自托管」。迁移本身不难（环境变量改一下就行），但向量回填和检索后端切换需要手工操作，不是无缝的。如果一开始就知道要上生产，直接选自托管或 Supabase 路线更省事。
